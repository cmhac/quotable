# Instructions for AI agents working in this repo

> CRITICAL: This document must be updated regularly to reflect changes to the codebase. Failure to do so may result in AI agents operating with outdated or incorrect instructions. This document is not intended to be a full record of every change made, but rather a high-level overview of the key instructions and guidelines for AI agents working in this repository.

## Project introduction

`quotable` is a small Python library that extracts tables from PDFs with a vision LLM and then checks every extracted value against the PDF's own text layer. The pipeline is: schema discovery, per-page layout discovery, per-page extraction, grounding (each value is looked up in the text layer), a position check (a value must sit in its own row and column), and a recheck of flagged cells. It is generic (not specific to any one document set) and was distilled from `scripts/extraction/extract_included_projects.py` in the VRA community-projects repository, which remains the reference for anything not yet ported.

## Project state

An initial, barebones port. The pipeline works end to end and the offline test suite passes (2,430 tests, no network, API key or PaddleOCR needed). Spec 001 (reject documents whose text layer is garbled or missing, before any model request) is implemented, and grounding cannot be disabled. Spec 002 (the recheck sends the page's whole text layer and tells the model to copy it, so the text layer wins over the model) is implemented. Spec 003 renamed the project to `gridkey` (package, distribution and the live-test model variable); behaviour was unchanged. Spec 009 renamed it again, to `quotable` (package, distribution, import, the default cache folder `.quotable/`, the logger names and the live-test variable `QUOTABLE_LIVE_TEST_MODEL`); behaviour and the test count are unchanged, and the README no longer explains the name. Spec 004 (several tables per document, including several on one page) is implemented: `extract_tables` returns one `Table` per table, discovery looks at every page in windows, and a table on a shared page is checked against its own band of the text layer only; its live check on the OCR'd Senate PDF (task 008) has not been run. Spec 005 (one entrypoint) is implemented: `extract_tables(pdf, model, *, cache_dir, max_requests, model_settings, discovery_pages, recheck, ocr, merge_reworded)` is the only public way in, `model` is a required argument (a pydantic-ai model string or `Model` instance, never read from the environment), and pydantic-ai with all provider SDKs (no PyTorch) is a regular dependency. The offline tests drive the pipeline through the internal `pipeline.run_pipeline(pdf, client)` with fake clients. The live test in `tests/live/` is opt-in (see Commands). Spec 006 (OCR with PaddleOCR, and an always-on cache) is implemented: when the text-layer check would reject a document, `extract_tables(..., ocr=True | False | OcrConfig)` OCRs only the bad pages (garbled or empty), checks again and carries on, and `Table.ocr_pages` lists the OCR'd pages; PaddleOCR is the optional extras `quotable[ocr]` (CPU) and `quotable[ocr-core]` (NVIDIA users add `paddlepaddle-gpu` themselves), imported only when a page misses the OCR cache; model answers and OCR results are always cached in `.quotable/` (or `cache_dir`). The NVIDIA path has never run on real hardware (checklist in `tests/data/README.md`), and AMD is not supported. The real-OCR tests in `tests/ocr/` are opt-in too. Not yet ported from the original: page orientation, histogram-based layout matching, adding schema-missing columns from header labels, the `incomplete` verdict and per-layout bands in the position check, splitting large rechecks, dollar-based cost caps (the cost is tracked, spec 011; nothing stops a run at a dollar limit), and a CSV/extraction-CLI writer (the DataFrames of spec 008 make a CSV one call). `README.md` lists these in "Not carried over yet"; what spec 004 does not handle is under "Not handled". Spec 007 (merge the parts of a table whose header is reworded between pages) is implemented: after extraction and before the recheck, `merge_tables` (in `steps/merge.py`) joins two tables only when they share no page, have the same column count, their names' words contain each other position by position without any cross-fit, their x grid matches within 10 pt, every column has the same dominant value shape (80%, at least 5 grounded cells per side) and each has exactly one partner; any doubt means no merge. It is on by default, `merge_reworded=False` turns it off, and `Table.merged` (a tuple of `MergedPart` with `MergeEvidence`) is the audit trail. The draft half-equal header rule was dropped on the golden fixture's evidence (it removed no harmful merge and cost correct ones; `Rules.equal_share` keeps it as a setting, default off), and one-word values count as `text`; `just score-merge` reproduces the numbers recorded in the spec. The fixture is `tests/data/synthetic/` (154 PDFs with truth files, made by `tests/synthetic.py` and `tests/synthetic_cases.py`, tracked in git; regenerate with `just synthetic`). Its live check (`tests/live/test_live_merge.py`, real model, 3 runs per case) passed 45 of 45; the `multilevel_gap` and `caps_flat_drift` ad-hoc cases have no fixture document yet (the generator draws single-row headers only). Spec 008 (DataFrame output) is implemented: `Table.to_pandas()` and `Table.to_polars()` return `records()` as typed frames (ints, strings as extracted, float coverage, null when never looked up); pandas and polars are regular dependencies given as ranges (`pandas>=3,<4`, `polars>=2,<3`) and are imported inside the methods, so `import quotable` loads neither; a library column whose name a PDF column already has (a PDF column called `page`) gets a trailing `_`, PDF columns are never renamed, and nothing raises (`table.output_names`). Spec 010 (extra fields) is implemented: `extract_tables(..., extra_fields=ExtraFields([...ExtraField | FieldGroup], prompt="", carry_forward=False))` reads values printed outside the tables (a page header) and puts them on every `Row` (`Row.extra`, `Table.extra_fields`) and in `records()`/the frames as `<name>`, `<name>__grounding`, `<name>__coverage`, `<name>__source_page`; discovery's window requests also return each page's fields (the request is unchanged without `extra_fields`, so cache keys are too); values are grounded against the page's whole text layer and count in `Row.status`, `flagged()` (`Flag.extra`) and `recheck_changes`; fuzzy/ungrounded values get one recheck (kept only if strictly better); the carry rule (`propagate`) is off by default and a `FieldGroup` clears the group's other fields on a page that prints one with an `exact`/`fuzzy` value; a missed-header check (words in a field's region outside the tables' bands) triggers one second look per suspect page, whatever `carry_forward` says. The fixture gained 20 `extra-*` documents (154 earlier files unchanged), `just score-extra-fields` scores the checks with injected faults, and the live test `tests/live/test_live_extra_fields.py` (never run without the owner's go-ahead) describes fields by position only so a request never prints a word of the header (`tests/extra_fields_live.py`, checked offline). Spec 011 (cost tracking) is implemented: `.quotable/` now has one subfolder per kind of thing (`cache/` for model answers and OCR results, `cost/` for the cost log), a cache that 0.1 left loose in `.quotable/` is moved into `cache/` once, every request that reaches a model (never a cache hit) appends a line (tokens and the genai-prices cost at the time, no prompts, answers or paths) to `.quotable/cost/requests.jsonl` through `PydanticAIClient(on_usage=...)` (`llm/client.py`) and `CostLog` (`storage.py`, which also holds the `.quotable/` layout and the cache folder), and `quotable cost-report` (also `python -m quotable`; `--dir PATH` for another project) sums the stored costs; a named `cache_dir` is used as given and costs still go to the working directory's `.quotable/cost/`; a write failure warns once and never breaks an extraction. The report's prices have never been compared with a provider dashboard (see `just test-live`). Spec 012 (package layout) is implemented: the package moved from `src/quotable/` to `quotable/` at the repository root, the 27 flat modules became 21 in four subpackages (`text/`, `ocr/`, `llm/`, `steps/`) plus `errors.py`, `pipeline.py`, `storage.py` and `table.py`, and `tests/` mirrors the subpackages; behaviour, public API, prompts, cache keys and the 1,442 tests are unchanged. `steps/recheck.py` now renders its page images with `render_png` from `steps/extract.py` instead of its own `dpi=150`. Inside the package everything except `quotable/__init__.py`'s exports is internal. Spec 013 (a local review app, `quotable review`, over runs saved to `.quotable/runs/`, with verdicts in `.quotable/review/`) is implemented (features plus the visual design, the mockup `specs/013-review-app/quotable review app.html`, a self-unpacking bundle; open it in a browser; 14 tasks in `specs/013-review-app/tasks/`, all done: position areas, the run format in `quotable/runs.py`, every `extract_tables` call saving its run to `.quotable/runs/`, the verdict and draft stores in `quotable/review/verdicts.py`, the queue, sampling and statistics in `quotable/review/queue.py`, and the browsing API in `quotable/review/browse.py` with its caches in `sources.py`; a handler may return `routing.Raw` for CSV, PNG and PDF answers, or raise `routing.ServerError` for a 500 with a message; the review API in `quotable/review/review.py`: `GET /api/queue`, `POST /api/verdicts`, `PUT /api/drafts`; the demo project of task 009, `just review-demo`, is built by `tests/review_demo.py` with fake models; the browser side of task 010: the app shell, the runs list and the run screen in `quotable/review/static/`, plain ES modules with no build step and flat file names because the server serves `static/` by name only, guarded by `tests/review/test_static.py` and node tests run from `tests/review/test_static_js.py`), the table, cell, queue and verdict screens of tasks 011-013 are plain ES modules in the same folder (`table.js`, `cell.js` with `pageview.js` and `cellview.js`, `queue.js`, `queuebar.js`, `verdict.js`, `shortcuts.js`). Pre-commit (`.pre-commit-config.yaml`) runs `ruff check --fix`, `ruff format` and `ty check` on every commit. The hooks are local hooks that call `uv run`, so they use the ruff and ty versions pinned in `uv.lock` rather than separately pinned hook revisions. Two things to know about the hooks: `pre-commit run --all-files` (and so `just hooks`) only covers files git tracks, so stage or commit new files first for it to see them; and a hook that auto-fixes a file reports a pass for a file git does not track yet.

## Spec-driven development

This project follows a spec-driven development approach, meaning that the specifications defined in the `specs/` directory serve as the primary source of truth for the project's functionality. The development workflow is as follows:

1. User requests features, bug fixes, and other changes, and the agent writes an initial specification for the requested change in the `specs/` directory. Agent opens a new branch for the implementation of the specification.
2. User reviews the spec and provides feedback or approval. If there are any open questions that need the user's decision, the user is required to provide clear guidance or answers before the agent proceeds with splitting the spec into actionable tasks.
   CRITICAL: DO NOT move to step 3 until all open questions have been resolved and the user has provided clear guidance or answers.
3. Agent splits the spec into actionable tasks that can be implemented in the codebase.
4. User reviews the actionable tasks and provides feedback or approval before implementation begins.
5. Agent implements the actionable tasks in the codebase, ensuring that the implementation aligns with the approved specifications.
6. User reviews the implemented changes and provides feedback or approval, completing the development cycle for the requested change.

### Naming conventions

- Each spec in the `specs/` directory gets its own folder, numbered serially using the format `nnn-feature-name`, where `nnn` is a three-digit number representing the order of the specification and `feature-name` is a brief, descriptive name for the feature or change being specified.
- Within the folder for each spec, the main specification file should be named `spec.md`.
- Tasks related to a spec should be placed in a `tasks/` subfolder within the spec's folder, numbered serially using the format `nnn-task-name.md`, where `nnn` is a three-digit number representing the order of the task and `task-name` is a brief, descriptive name for the task.
- After initial task implementation, if the user requests any changes or modifications to the written code, spec deltas may be created in a `deltas/` subfolder within the spec's folder, numbered serially using the format `nnn-delta-description.md`, where `nnn` is a three-digit number representing the order of the delta and `delta-description` is a brief, descriptive name for the delta.
- Specs 001 to 011 refer to modules by the paths they had when written (flat `src/quotable/*.py`) and are not rewritten; spec 012 moved them (its `spec.md` maps old to new).
- Specs 001 and 002 keep the project's former name, `pdf-table-extract` (import `pdf_table_extract`), and specs 003 to 009 keep `gridkey` (import `gridkey`; spec 009 describes the rename to `quotable` itself), because they record decisions made under those names. They are history and are not rewritten. The folder `specs/003-rename-to-gridkey/` keeps its name for the same reason.
